### Завдання 6. Висновки
1. **Відношення порівнянь простого й швидкого сортування на `n = 10 000` проти лекційного `376`:**
   Лекційне число $\frac{n^2 / 2}{n \log_2 n} = \frac{50\,000\,000}{132\,877} \approx 376$ рахує ідеальний середній випадок для вставкових алгоритмів проти чистого $n \log_2 n$. У нашому замірі відношення відрізняється (зазвичай становить близько **150–250**), оскільки на випадковому масиві вставки роблять у середньому $n^2 / 4$ порівнянь (ранній вихід із внутрішнього циклу `while`), а `QuickSort` із медіаною трьох витрачає додаткові порівняння на обчислення медіани на кожному рівні рекурсії.
2. **Дві причини, чому `Array.Sort` швидший за власний $O(n \log n)$ алгоритм:**
   * **Відсутність викликів делегата `Func<T, T, int>` на кожне порівняння:** `Array.Sort` для примітивних типів (`int[]`) використовує вбудовані інструкції процесора напряму без накладних витрат на непрямий виклик делегата та обгортки порівняння.
   * **Гібридний алгоритм IntroSort:** `Array.Sort` поєднує швидке сортування для великих ділянок, сортування вставками для коротких відрізків ($\le 16$ елементів) та пірамідальне сортування (`HeapSort`) при глибокій рекурсії, уникаючи зайвих витрат пам'яті та викликів функцій.
3. **Вибір алгоритму для 100 000 записів (цілий ключ `0..300`, щоденне сортування, обов'язкова стабільність):**
   Найкращим вибором є **сортування підрахунком (`CountingSort`)** з проходом вихідного масиву справа наліво під час заповнення результату. Діапазон ключів крихітний (`301` значення проти `100 000` елементів), алгоритм працює за лінійний час $O(n + k)$ без жодного порівняння ключів і гарантує сувору стабільність.
